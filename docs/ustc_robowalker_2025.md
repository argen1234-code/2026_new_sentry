## 2. 机械（简述）

- 参考 RUMC2024 哈工大哨兵，融合过隧道需求。
- **两舵轮 + 两全向轮的后驱车**：减少打滑、提供稳定轮速计、高上坡能力，
  并且在一定定位误差下可以「撞进」隧道。
- **大小云台**：高载弹、高云台响应、自瞄时电机转速基准一致。
- **雷达置于底盘上**：雷达固定刚度高、位姿差稳定、视野尽量大。
- 国赛配置：主摄 CS016-10UC + 5 mm F1.4，辅摄 CS020-10UC + 6 mm，算力 NUC Ultra7-155h。

## 3. 嵌入式（底盘）

作者：刘彦宏。**六层架构**：应用层（CAN/USB/UART/定时器回调、主循环）→ 功能模块层（底盘/云台/
发射机构，用类封装）→ 硬件驱动层（达妙 H7 板载、M3508、GM6020、翎控、遥控器）→ 中间件层
（PID 与矩阵/限幅/字节序工具）→ 硬件抽象层（HAL 外设再封装）→ CubeMX HAL。
工具链 armgcc + cmake + make，CLion 开发。

**关键事实**：这套哨兵**没有超级电容**，底盘在大约 **85 W** 最大功率下运行。

### 3.1 底盘解算：力控

流程：期望 `vx/vy/wz` → 速度解算得舵向期望方向与轮向期望速度 → 由当前轮速反解车体速度 →
PID 求期望力与力矩 → 力分配解算得各轮力矩 → 功率控制。

- **正向运动学**：由车体 `[vx, vy, wz]` 直接得到四个轮（含舵轮）的期望速度，解析式简单。
- **逆向运动学**：要解 4 轮速度 → 3 个车体量，是**超定**方程。作者先用 Moore-Penrose 伪逆
  （常数矩阵，可预计算）求最小二乘解，但指出两个问题：结果不光滑（对力控 PID 不友好）、
  难以处理**某轮打滑**的情况。最终改用 **Kalman 滤波**做反解：输入四轮速度，观测车体速度与角速度，
  假设车体速度/角速度恒定，在惯性系下换算，用 `A⁺` 作转移矩阵；`Q`、`R` 先定一个再按效果调另一个。
- **力分配**：轮向力矩求解是**欠定**线性方程组（3 个独立方程、4 个未知量），解在一条直线上。
  做法是取伪逆的最小解后再**沿零空间微调**：先解出零空间非零向量并单位化（首分量取正），
  与上一周期的向量做内积检查方向一致性；再找相对转速最低的轮子（需要更大力矩），
  按符号逐步增大/减小零空间系数。这解决上坡时前侧全向轮打滑、后侧舵轮转不动的问题。
  对「不正常打滑」（某轮悬空、相对转速远大于其他轮）则**直接把该轮力矩置零**直到恢复。
- **功率控制**：单电机建功率模型（系数由采集数据最小二乘拟合）。策略是先保舵向电机功率
  （超限则整体乘功率因子，解二次方程），再算可分配给轮向电机的功率，超限时给**所有轮向电机乘同一个
  电流因子**——刻意不破坏力分配解算的结果。最后再按 M3508 的 20 A 电流上限统一限幅。

## 5. Batch-LIWO（里程计）

### 5.1 系统设计

- 状态量 **SO(3) + ℝ²¹**：世界系 IMU 位置、速度、陀螺零偏、加速度计零偏、**重力**、
  **IMU 角速度**、**IMU 加速度**。
- 沿用 Point-LIO 的写法，把**角速度也写进状态量**：好处是可以用测量噪声自然描述 IMU 噪声，
  并且在陀螺/加速度计**饱和**时可以放弃 IMU 更新、只用雷达点更新来保持稳定
  （作者提到 MID360 内置 IMU **4 g 饱和**，二次积分求位移容易发散）。

### 5.2 基于 Batch 的更新

Point-LIO 是逐点更新，理论上把 MID360 变成 20 万 Hz 传感器，极端动态下稳定性好，
但代价是：难以并行化、必须挑关键点、要控制参与更新的点数量。

于是改成 **Batch 更新**：把约 **1 ms** 时间窗内的所有点按状态量变换到同一时间戳，
逐点算残差后**拼接残差与测量矩阵再一次 Update**。好处：

- 每个点以相同置信度更新，Update/Predict 次数大幅减少，效率显著提升；
- MID360 非重复扫描在极短时间内会扫到多个平面（4 条激光线），一个 Batch 内含多个平面的信息，
  **有效约束了自由度**，缓解单次 Update 自由度更新不全的问题。

### 5.3 轮速融合（重点）

动机：观测退化（隧道、撞击、高转速）时纯 LIO 不稳；轮速是**高带宽、无累积误差**的测量源。

- 残差定义在 **IMU 坐标系**下；协方差 = 「期望残差的倍数 × 基准噪声」。
- **期望残差的度量**：
  1. 用当前轮速与舵轮角度做**最小二乘**，得到无打滑假设下的底盘速度；
  2. 把这个速度按舵轮角度**投影回四个轮的期望轮速**，与实际轮速做等权平方和。
- 这个度量刻意**保守**：单轮失效时会大幅降低轮速置信度。作者的原则是
  「允许某个观测源被短暂误判为失效（还有 IMU 和点云兜底），但不能容忍它给出错误的速度更新」。
- 反面案例：国赛时**底盘掉电后反馈了错误的高置信度轮速**，导致里程计漂移、打 RPS 时乱跑；
  赛后严肃修正。

### 5.4 工程实现与指标

- 参考 Point-LIO 重写了传感器队列、独立线程、主处理逻辑，目标「简化逻辑、提高稳定性与效率」。
- 开源地址（文中明示）：`ZhangHaopeng-Dino/Batch-LIWO`。
- RoboSense Airy 包太大，做了**共享内存**传输的 `shm_lio_bringup` 与 `RoboSense-Driver`；
  也改了 Livox ROS Driver 以降负载。最终选用 **Mid360**（非重复扫描对里程计场景「没有平替」）。
- 为后端点云密度需求，额外输出**完整点云**：被降采样丢弃的点排队按时间升序，
  每次 update 后用新状态做一小步前向预积分，对齐时间戳变换到世界系。
- 实测：Intel NUC 1240p **单线程 6 万点/秒**（不含降采样丢弃的），占用 30–40%；
  **20 小时无内存泄漏、CPU 负载不上升、延迟不变**；**14 rad/s 小陀螺稳定、3 m/s 冲撞稳定**。

### 5.5 全局定位：故意不做独立模块

- 做法：把预建点云与初始位姿（`xyz + yaw`）直接给 Batch-LIWO（预构造 iVox）。
- 启动摆放容差：**约 20 cm 位置、30° yaw** 内可稳定启动（国赛实测）。
- 理由：LIO 本身已基于 ICP 思路，再叠一个简单 ICP 没有提升；而加随机采样会让负载和模块间
  时间同步变得不稳定——「稳定不跳变的里程计是后续所有模块的基础」。
- 结论：把精力放在**里程计本身的鲁棒性**上，而不是重定位模块。

## 6. 感知

### 6.1 3D 占据栅格（ROG-Map 改造）

以 HKU MARS 的 [ROG-Map](https://github.com/hku-mars/ROG-Map) 为基础（RoboCentric 3D Sliding Map，
贝叶斯增量占据、射线清除、体素化输出），本队改进：

1. **移植到 ROS 2**；
2. **分开定义雷达中心与机器人中心**：机器人中心是地图中心，雷达中心是 raycasting 的出发点。
   地图下限压到地面以下一点，减小存储与滑动开销；同时避免雷达与机器人中心不重合时的小陀螺
   引起**无意义的地图滑动**；
3. 用 **TBB 重写 raycasting 等可并行部分**（导航是定时流水线，单模块降时延是合理的）；
4. 增加 **Fading（遗忘）**：原版对被长期遮挡的障碍点一视同仁、永不消失（空旷场景里旧障碍会
   永远留在地图里）。实现方式是**再维护一张时间戳图**，占据时写当前递增计数，地图滑动时同步裁剪，
   更新后检查超阈值即清除。

指标：**2.5 cm 分辨率、10×10×1 m** 局部地图，Mid360 完整点云（丢弃无效遮挡点后约 8 万点/s），
50 Hz 下约 **6 ms/帧、30% 时间占用**。联盟赛版（倒置雷达大小云台哨兵）在 10×10×**0.8 m**、
**0.1 m 分辨率**下约 **4 线程 10% 帧时间（2 ms/50 fps）**。

### 6.2 障碍识别：为什么放弃传统分割

试过 PatchWork++、LineFit Seg、PUTN 及各类特征分类，实时性与可靠性都不达标
（「一个点分错就可能让机器人不选那条隧道」）。

自研传统方案：结构化点云转两张 2D 灰度图（最低高度、最高高度）→ 作差 → 简单滤波 →
3×3 方差 → 阈值分割。问题：点云不稠密、raycasting 有空洞导致高度差不准；调参敏感，
不适合 RM 的高动态场景。**放弃**。

**最终方案**：直接利用前端输出的**结构化**栅格，对每个离散 `(x, y)` 做**高程分析**：

- 高度差 `H` = 最高点 − 最低点；
- 占据率 = `(n+1)·res / H`（`n` 为两点之间的点数）。

理由：RM 场景的墙大多是竖直的，雷达扫到的是平面，加上前端结构化降低了面噪声，高程分析很稳。
测试下来鲁棒性与效率都很好。

**动态障碍**：占据栅格的原理性缺陷是会留下**尾迹**。作者不试图消除尾迹，而是**把尾迹当观测**：
记录尾迹上每个点的更新时间，对**同一更新时间且彼此邻近**的点聚类，再用匀速模型卡尔曼滤波 +
卡方检测跟踪。精度一般，但「对纯雷达方案而言也差不多了」。（文中注明这部分没上场、测试不多。）

## 7. 规划

### 7.1 障碍梯度表示：选 ESDF 而不是安全走廊

先试了膨胀地图 + 矩形安全走廊（参考哈工大 RMUC2024 调试图），遇到四个问题：

1. 赛场隧道是**斜的**，体素化误差导致通道宽度不一致；
2. 隧道**偏长且带转角**，不适合构造走廊；
3. 动态障碍无法优雅处理（不可能每个预测时间片重算走廊，CBF 也难以与走廊结合）；
4. 避障是软约束，**出了走廊才给梯度**，狭窄地形容易优化出穿障碍的路径。

改用 **2D ESDF**：场地图预构造的 ESDF 可以很精细（实测 5 cm 分辨率）；
受 RC-ESDF 启发可把每个运动障碍物的 ESDF 独立出来，每个时间点取「场地 ESDF 与各动障 ESDF 的
最小值」；还能通过设置梯度介入半径灵活控制离障碍的距离。

ESDF 的缺点与对策：

| 问题 | 对策 |
|---|---|
| 时间调整不灵活（不如走廊） | 对 JPS 结果做**细致的重新采样** |
| **梯度震荡/无效化**：峡谷形障碍中间两格距离相同 → 梯度为零 | **二次函数插值**：在 2×3 邻域用三个点拟合二次函数，平滑距离与其切线斜率（梯度） |
| L-BFGS 不收敛（线搜索超限） | 放宽终止条件 + 迭代次数上限 + 参考 DDR-opt 的提前退出条件；并改为**两次优化** |
| 实时性 | 实测 0.1 m 分辨率、全场重建 **2 ms**（单线程），所以每帧**完全重建**，不做增量 |

（原计划 RMUC2025 实装 FIESTA 式增量 ESDF，赛季内未做。）

### 7.2 前端：JPS + 时间重分配

- 选 JPS：无权重栅格、无预处理下最快的寻路算法。
- 不选 Kinodynamic A*/RRT*：局部性太强，难以利用全局信息。
- **思路一（梯形加减速重采样）**：记录相邻两点连线长度和 `s1`、相邻三点转角总和 `s2`，
  定义距离 `s = k1·s1 + k2·s2`（`k2` 一定程度表征轮距），按 `amax/vmax` 的梯形加减速求总时长 `T`，
  再按期望时长等分重采样。
- 问题：JPS 轨迹不平滑，简单重采样会在**折角处明显变慢**，导致后端优化失败（轨迹扭成麻花或
  时间特别长）。
- **思路二**：先把思路一的结果做一次**放松时间与碰撞约束的 Minco 优化**，再按估计总时长
  均匀重采样。（比「用 JPS 给 Kinodynamic A* 做启发式」实现更简单，也不多引入模块。）

### 7.3 轨迹表示与优化（Minco + L-BFGS）

基于 [ZJU-FAST-Lab/GCOPTER](https://github.com/ZJU-FAST-Lab/GCOPTER) 修改到本队版本：

- 移植到 ROS 2；
- 用 **ESDF 梯度**替代安全走廊；
- 把无人机的 3D 微分平坦模型换成**二维全向微分平坦模型**（大幅简化）；
- 设计基于 ESDF 与 2D 模型的梯度计算；
- **两次优化**；删掉其余所有不需要的代码。

**两步优化**（这是他们认为提升可用性最大的一处）：

- `PRE_OPTIMIZATION`：直接用二次插值梯度，不分沿轨迹/垂直轨迹方向。简单，但在狭窄隧道前后
  控制点会被**推离隧道**，控制点间距变大 → 速度分配错误 → 需要额外减速段。
- `FINELY_OPTIMIZATION`：
  1. 把梯度减去沿轨迹速度方向的分量，得 `gradPos`；
  2. 沿 `gradPos` 采样一步后的 ESDF 值，判断该方向能否自由移动（梯度接近 1 说明可以），
     否则按 `scale·√‖gradPos‖` 处理 `violaPos`（软约束特殊处理），阈值取 **0.5**；
  3. 另加速度/加速度约束项（平方减阈值平方），并把三类梯度汇总到后段控制点。
- 第一次优化还加了**段时间约束**（相对平均段时间的上下限 0.9–1.1），否则控制点会被推出窄道。
- 效果：两次优化各 ≤10 ms；控制点数量可以大幅减少。

**耗时**：文中两处数据——总览说规划稳定性提升的同时把计算从 **80 ms 降到 10 ms**；
优化章节说一条 30 m 轨迹曾需近 **100 ms**，调参 + 迭代上限后稳定在**单线程约 80 ms** 以内。
（口径不同，前者指单次优化，后者指整条 30 m 轨迹的完整优化。）

### 7.4 重规划

利用 Minco「轨迹必过路标点 + 路标点带时间戳」的特性：

1. 起点取实时里程计位置在轨迹上的**最近投影点**；为了避免重规划跳变，**往回保留一小段已走过的
   轨迹**拼到新轨迹前端再送优化；
2. 轨迹可以只用「路标点 + 初始速度 + 各点时间戳」在模块间传递并**完全复现**；
3. 梯度最终汇总到路标点上，所以可用 L-BFGS 这类无约束优化器直接操作路标点。
- 三种重规划策略：全局重规划、仅优化、部分重规划；并有把起点/终点推出障碍物的策略。

## 8. 控制：SE2 MPC

### 8.1 选型理由

对比 PID / Pure Pursuit / MPC：

- PID 难以利用未来轨迹补偿延迟、难以施加约束；
- Pure Pursuit 有前瞻但更适合自行车/阿克曼模型，对**全向底盘**不合适，且难以加严格约束；
- MPC 转成**线性运动学约束下的 QP**：能前瞻补偿延迟、能直接加运动学/动力学/摩擦约束、
  调参直观。**最终选 MPC**。

### 8.2 建模与求解

- 线性离散模型：状态 `[x, y, yaw, vx, vy, wz]`，控制量 `[Fx, Fy, Mz]`，
  `A`/`B` 由质量 `m`、转动惯量 `Iz`、步长 `dt` 构成。
- 目标函数：状态跟踪误差 + 控制量平滑，展开成标准 QP；约束含速度上下限、控制量上下限、
  **全向舵轮摩擦力约束**（线性化后并入不等式约束）。
- **稠密 QP + qpOASES**：Hessian 与约束矩阵是**时不变的**，可预构造；
  40 步预测时求解平均 **1 ms 以内**。

### 8.3 三个工程要点（最值得抄的部分）

1. **定位同步与估计**：上游 Point-LIO 100 Hz、IMU 200 Hz、轮速 1000 Hz。用 ROS 2 时间戳同步，
   再基于**有延迟的里程计位姿**，用高频轮速与 IMU 做局部积分，估计最新位置与角度。
2. **二次期望轨迹（横向误差优先）**：首次规划投影处的状态与机器人实际状态可能差很多，
   若沿 `x/y` 权重相同，纵向误差会「淹没」横向误差，导致过窄缝时卡住。
   作者不用 Frenet（大曲率下线性化误差大、有奇异点），而是**按首次规划与期望轨迹对应时间点的
   速度法向夹角余弦缩小时间步长重采样**——主动牺牲一点纵向速度，换横向精度。
3. **命令前瞻**：取起始时间 +**10 ms** 处的规划速度作为下发命令，补偿 QP 求解、通信、下位机 PID 的延迟。
4. **底盘朝向策略**：小陀螺前进 / 底盘跟随轨迹切向两种模式，按「Minco 控制点到 ESDF 障碍的距离」
   判断狭窄程度自动切换；进窄缝前把底盘前方转到切向正方向，进窄缝后**就近**转向切向正或反方向，
   避免卡死。

**作者自己指出的坑**：为了简化调试，他们**没有把 MPC 规划的力作为前馈发给下位机**，
只在轨迹起点低速时设了速度下限。结果起步加速时速度指令太小、下位机 PID 推不动，
**「或许是场上若干次卡在隧洞入口处的原因」**。作者认为 MPC 的最佳实践仍应下发力前馈，
但那会带来额外震荡调试成本。

## 9. 自瞄（只记路线与指标）

基于开源 RM Vision 重构为 RW Vision，赛季内重点补短板：高性能 IMU 模块、全自由度 IMU-相机标定、
Bayer 图像灯条角点提取、对齐观测器的 PnP 与 yaw refine、灯条被装甲板遮挡导致的观测长度变化建模、
更自然的观测器噪声表述、IMU-相机时间同步、MPC 云台与开火控制器。

**Bitter Lessons**（作者原话要点）：

- 硬件与硬件标定至关重要；**陀螺仪 Bias / Latency 每晚标定**直接影响次日表现。
- **MPC 路线正确**：一年没调的云台 PID 追不上高速小陀螺，MPC 把问题建成优化问题后
  「彻底解决了又超调又滞后」。
- **MPC 调试难**：直接力控云台难驾驭，最终在双环 PID 上加力矩/速度前馈，调了若干天；
  前瞻时间等参数一改就震荡，**没经验的队伍谨慎尝试**。
- MPC 上限取决于机械传动：同一份代码，哨兵几乎零延迟，步兵有约 10 ms 滞后。
- 硬件会骗你：服役三年的 NUC 振动后自己关机，最后两个比赛日才发现并更换。

国赛数据：弹频 18 发/s，目标 18 rad/s 小陀螺下能以 50% 开火时间开火；综合命中率 **32.2%**（最高）、
局均伤害 **1184**（最高）、最高哨兵 KDA **6/0/5**、最高单局伤害 **2577**。

## 11. 与本工程的对照（我的观察，未实测）

我们现状是 `point_lio → small_gicp 2 Hz 出 map→odom → Nav2（costmap + theta_star + 全向 PID
追踪）`；他们是**自研全栈**，两边不在同一抽象层次上，但有几处直接对应我们的痛点：

| 我们的问题（memory 记录） | 对应他们的做法 |
|---|---|
| 平移方向系统性偏 24–29°，没有轮速参与的里程计 | **轮速以低置信度融入 I-ESKF**，并给出期望残差的度量；尤其「单轮失效就大幅降权」这一保守策略 |
| 窄口净宽 0.62 m、可规划带仅 0.10 m，plan 擦挡板 | **ESDF 梯度无效化**用二次插值解决；**两根窄道之间**用两步优化避免控制点被推出 |
| 过弯切内线、贴挡板到 0.18 m 被判「起点在障碍里」 | 他们用 **MPC 二次重采样按速度法向夹角缩步长**，牺牲纵向保横向；我们用的是固定前瞻的追踪 |
| 静止时 `/map` 0x0 导致规划死锁 | 他们干脆**不用 2D 栅格规划**，全部走 ESDF；且障碍识别直接吃结构化栅格 |
| 底盘速度环死区、静摩擦 | 他们是**力控 + 力矩分配 + 功率控制**，根本不用轮速 PID 直接给电流 |

可以低成本借鉴、不需要换栈的：

1. **轮速置信度度量**：即使不做轮速融合，也可以用「最小二乘解 → 投影回四轮 → 加权平方和」
   这一套来**在线检测打滑/悬空**，作为底盘健康度上报（我们现在只能靠 `/chassis/state` 事后看）。
2. **狭窄地形先用「主动减速」换横向精度**：他们在控制器里做，我们在 Nav2 参数里做
   （上一轮 `curvature_forward_dist` 收窄思路一致，但力度可以更大）。
3. **规划前的「起点/终点推出障碍物」策略**：我们目前是规划器直接拒绝（theta_star 报
   `start pose is an obstacle`），他们有一层专门的推出逻辑，可以让规划从「卡住的姿态」恢复出来。

**不建议直接移植**：他们的栈与我们的 Nav2 体系不兼容（自定义轨迹、自定义控制器、无 costmap），
换栈等于重写导航；且代码尚未开源，现在只能借鉴思路。
